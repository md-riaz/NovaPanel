# Protected effects require managed process lifetimes

## Delegated ruling before implementation

This is a new internal mechanism ruling under the Phase 4 ConfigIsolation design delegation, based on published `eeb630ff4e34629e84169c617f464e6f2f75a332`. It does not authorize production activation, replace independent review, or complete the phase. F6/F7/F10/F12/F15/F19, phase-4 compatibility PHP, numeric credentials, sealed original-job recovery and deferred final VM acceptance remain binding.

Select a root-controlled cgroup v2 **domain** for every supported managed site-account lifetime. Descendant processes remain supported. Do not delegate cgroup migration or control files to the site UID. Admission must place the initial process in the domain before it can execute site code or receive a credential. Fork, double fork, setsid and exec then inherit membership. A PID scan followed by migration is not an admission mechanism. A UID is a credential, not a cgroup membership rule.

Protected effects require terminating and draining the pre-existing untrusted site workload, not merely freezing it. `cgroup.kill=1` handles concurrent forks; wait for recursive `cgroup.events populated=0` before admitting the effect. A failed kill, inaccessible domain, mismatched lifetime, deadline or nonempty domain means no protected effect and no serving restart. Freezer acknowledgement only stops tasks. It does not establish cancellation of previously submitted kernel asynchronous IO, revocation of writable mappings/descriptors, or absence of delegated writes to another process. No freezer-only adapter is approved.

This deliberately permits a disruptive maintenance interval for a protected operation. It does not silently promise restoration of arbitrary background jobs. Automatic restart of untrusted workload before successful installation/reconciliation is forbidden. Normal serving publication remains a separate verified transition.

## Supported account lifetime, not account enumeration

Before the first process can use a newly provisioned numeric UID, the provisioning owner durably binds the original site/job identity, username, UID/GID, canonical home and cgroup identity to a managed lifetime. It must own exclusive allocation of that numeric UID. The managed account is non-login, unprivileged, with empty supplementary groups and no capability/setuid route to another host identity. Every privilege-changing launcher for that UID must participate, including FPM master children, credential runners, later cron/deploy/SFTP and trusted operator tooling. No root broker may launch the UID outside its domain. No site may pass writable target descriptors, writable mappings or delegated write requests to an uncontained peer. Such peers must be included in the writer set or refused by the supported deployment contract.

This is a controlled fresh-account contract. Existing accounts with unknown process history cannot be adopted after a successful `/proc` or getent scan. They require a separately reviewed offline migration, with all launchers disabled and writer/IO lifetime established before admission. Merely deleting/recreating a passwd entry does not retire the numeric UID. Retained files/config, pending operations, live processes, writable descriptors/mappings and external writer brokers all survive account-database edits. UID reuse must remain forbidden until explicit retirement proves those authorities absent. Interrupted recovery retains the original lifetime, not a fresh account with matching text fields.

A root-owned lifetime admission owner closes all managed launcher admissions before draining. It also excludes managed account deletion, UID/GID/home replacement and managed root relocation for the entire protected operation. It holds this exclusion across filesystem checks, config publication, admitted credential children and their drain. The existing operation locks remain required but do not supply this broader lifetime owner.

Independent privileged operators remain trusted. They must refrain from account changes, process migration/launch, cgroup replacement, mount/rename/relocation and writes affecting the protected tree while its managed lifetime is held. Cooperative operator tooling must acquire the same exclusion; raw hostile root can bypass it. Neither flock, getent, pidfds, no-follow descriptors nor cgroups constrain hostile root. Detectable pre-effect identity/path mismatch refuses; detecting a change after effect is recovery failure, not evidence that no change occurred.

## Concrete sequence and next consumer contract

1. Under the original operation's complete ordered lock set, acquire the managed account lifetime and trusted-root maintenance exclusion. Check non-serving state and the original sealed identity/expiry. Close all launcher admissions. Persist the non-serving/recovery disposition before any process or filesystem effect. A canceled acquisition must not reopen admission.
2. Revalidate held root-controlled cgroup v2 domain identity and ancestry. The agent itself and unrelated workloads must not be inside the target domain. Kill the untrusted subtree and wait for recursive absence. Drain every admitted root launcher and its process creation before accepting emptiness. Recheck account/home/docroot identity while exclusion remains held. A global UID scan may diagnose unsupported contamination; it cannot establish this step's invariant.
3. Establish filesystem IO quiescence after process exit. Explicitly account for submitted native AIO/io_uring, shared writable mappings, transferred descriptors, network/FUSE or other external writer brokers. A kernel/filesystem-specific drain proof or a restricted supported backend is required. `populated=0` by itself is not that proof. Do not publish configuration while this proof is absent.
4. Admit only the original operation's reviewed bootstrap children into a separate controlled execution domain. Enter at birth before privilege drop/execution and secret delivery. Keep untrusted admissions closed. Each reviewed step must finish and its entire domain must be empty before subsequent filesystem custody verification. Direct-child Wait or process-group cancellation alone is insufficient. Do not return a generic reusable launch capability.
5. `ConfigIsolation` invokes its callback synchronously once only after steps 1 through 3. The outer operation lifetime, not the config callback alone, must cover subsequent credential children and core install. Cancel and drain admitted calls before releasing protection, including worker return, panic, cancel and retained asynchronous callers. On any ambiguous effect preserve original-ID sealed recovery and keep serving disabled. Do not reopen admission in an unconditional defer.
6. After SQLite/audit reopen, recover the same journal, account lifetime and domain identity. Verify no outstanding launch can complete after the empty observation. Revalidate protected bytes, keep credentials/salts unchanged, and obey the unchanged 24-hour expiry and atomic terminal/claim contract. Successful terminal publication alone does not authorize reopening a failed process domain.

The next consumer must expose one operation-scoped held lifetime, not independent success booleans for account lookup, FPM stop and empty PID scan. It must own admission, kill/drain, IO quiescence, reviewed child execution and explicit successful serving release. No nonnil callback may substitute for those missing responsibilities.

## Unavoidable architecture work outside this file scope

The current shared `php8.3-fpm.service` master can fork workers for several UIDs from one cgroup. It cannot supply at-birth per-site cgroup membership without another trusted mechanism. Moving discovered workers afterward leaves the fork-before-migration hole.

Recommended minimal per-site solution is a dedicated root-supervised FPM master/service in each site's domain, retaining the canonical PHP 8.3 binary, pool contents and nginx-owned socket. This changes the canonical shared-unit reload assumption and requires explicit parent integration ownership for FPM orchestration and packaging. The alternative is one managed domain for the shared FPM master plus **all** managed site launchers, with server-wide PHP/background-work maintenance for every protected effect. That has a smaller service change but a larger availability consequence; it must not be disguised as per-site quiescence.

`internal/exec.RunOpts` currently has no held cgroup descriptor or at-birth placement and `Real.Run` waits only its direct child/process group. A reviewed F15-compatible extension using Go's Linux `SysProcAttr.UseCgroupFD/CgroupFD` and kernel `CLONE_INTO_CGROUP`, plus whole-domain termination/drain, is necessary. This task does not edit the shared runner/drain files. Placement failures must refuse; never fall back to spawn-then-migrate. Unsupported seccomp/kernel/service layouts fail closed.

Before claiming physical writer quiescence, the parent must also select and verify the IO-drain/backend contract in step 3. Killing a process and seeing no live cgroup tasks is necessary, not a proof that all asynchronous effects have completed. This is the remaining architecture choice, not a reason to ship a success callback. Recommended first supported scope is fresh install on an agent-controlled local filesystem with no prior site execution or external writer authority; enable existing-site protected mutations only after their IO retirement proof is reviewed. This restricted first scope does not claim rotation or arbitrary existing-account support.

## Evidence and acceptance ownership

Safe numeric-child probes use only internal/exec, injected account data and pre-opened scratch descriptors. They create no account, service, cgroup, mount or PHP process. They can falsify process-group, chmod and enumeration hypotheses; they do not emulate or prove kernel cgroup containment. Production cgroup and asynchronous-IO drain acceptance requires a disposable reviewed fixture or final VM, never host cgroup mutation under this delegation.

Required end-to-end acceptance remains the handoff's complete failure matrix: pre-existing non-FPM writer, concurrent fork during acquisition, changed UID/GID/home, managed relocation exclusion, hostile-root limitation, retained asynchronous invocation on return/panic/cancel, blocked acquisition/drain cancellation, missing/unquiesceable dependency before effect, original-ID SQLite/audit reopen recovery and unchanged secret projections. Existing worker-drain tests cover only worker-owned admissions, not all-site-UID isolation. New mechanism tests must start RED at the agreed lifetime/operation seam before implementation; characterization of current limitations is not GREEN for the future mechanism.

These define process membership/control and asynchronous submission, not an all-filesystem drain guarantee.
