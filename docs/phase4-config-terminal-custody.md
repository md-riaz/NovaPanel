# Protected config terminal custody ruling

This delegated slice removes only the encrypted `<job-id>.sealed` record after successful operation-owned terminal publication. It never deletes `wp-config.php`, temporary files, unmanaged entries, failed or expired operation records. Failed/expired effect reconciliation remains separate because terminal failure does not prove filesystem rollback.

The queue receives an explicit trusted custody-root dependency, not an RPC path. It reconciles successful WordPress operations after the existing audit-before-terminal sequence and at startup before admission. SQLite must initially prove the original WordPress operation and job are done, input ciphertext is destroyed, the committed site/database/WordPress binding still matches, and the exact successful worker completion audit is mirrored. The existing atomic terminal transaction establishes claim publication. A surviving claim must be published or consumed; an absent claim is permitted because consumption/expiry deletes it. No new schema or plaintext metadata is introduced.

The filesystem consumer authenticates the sealed record against the complete operation binding, holds a no-follow root-owned custody directory, and checks the held record inode against the directory entry immediately before unlink. It removes no other entry. Trusted root relocation and concurrent root writers remain excluded by the dependency contract and existing operation locks. It makes no current-docroot-path attestation. Missing records are idempotent, with directory sync on retries. Cancellation or cleanup failure refuses startup admission and retains the committed outcome without rerunning effects or recreating claims.

## Delegated lifecycle correction

A done WordPress journal may record `ConfigCleanup` in its existing typed identities JSON. The only nonempty values are `authorized` and `acknowledged`, and they are valid only on successful WordPress journals. This is secret-free ownership evidence, not new DDL or a deletion exception. Before recording `authorized`, the queue must prove the original live binding, destroyed inputs, terminal job, mirrored success audit and claim publication under the operation locks. Persist this authorization before touching the sealed record. Once authorized, that historical ownership survives supported deletion or rebinding, including a crash after unlink before directory sync. Every retry still validates terminal job/audit/claim evidence and authenticates any present record against the original binding before removal.

Only after successful directory sync may the queue persist `acknowledged`. An acknowledged journal no longer requires a live site binding, but it must still prove terminal evidence and no-follow absence in the trusted custody directory, then sync that directory. Any present entry, including a restored authentic old record, is a conflict and refuses startup without removal. Missing unacknowledged records do not waive the initial live-binding authorization check. SQL acknowledgement failure leaves durable authorization for a missing-record sync retry, never replay or claim regeneration. The expired-operation `reconciled` bit retains its original meaning. No live configuration file is opened by either cleanup path.

Production isolation, staged artifacts and final VM/power-loss acceptance remain unpassed. This adds no default production wiring or publication authority.

## Durable failure audit identities

Version 1 operation identities may contain an optional PHP `FailureEventID` and publication `FailureEventID` with `FailureCode`. Each is a valid distinct ULID; publication failure code is one of `agent_error`, `interrupted`, or `conflict`, and both publication fields are present or absent together. The queue persists these identifiers in the operation transaction before the file-first append. A `publication=not_committed` observation uses stage `publication`, not a terminal execution outcome; the restored PHP failure uses stage `exec` and `publication=restored`. The success intent is not a committed outcome. Retrying uses the same ID and payload, and uncertain terminal SQL responses require durable readback and closed admission. Audit failures remain sticky until reopen and file-to-SQL replay.
