# Internal terminal reconciliation ruling

Delegated decision for the next bounded implementation after b92c84f. This is not production activation or Phase 6 completion.

Canonical authority is docs/spec/phases/phase-6.md, especially the journal authority and daemon-only reconciliation contract. The existing events table and canonical fw_pending testdata suffice. Production migration 0007 remains absent pending 0006.

The daemon-side audit Log will reconcile through the existing journal lock. The Store transaction acquires the SQLite writer lock, validates the matching pending ID, exact unit, millisecond deadline equal to journal seconds times 1000, and confirmed=0. SnapshotPath is not trusted or opened by reconciliation. Journal metadata cannot prove a SQL snapshot pathname, and the journal's ID-bound verified digest remains the recovery authority. Any other pending row or mismatched projection fails closed.

A deterministic recovery event uses the pending ID as its event ID. Existing event-ID collisions fail closed unless every event field matches. Its actor is firewall-recovery, not an invented client identity. Its verb is firewall.confirm or firewall.revert and its detail contains the full metadata-only terminal journal record. Its timestamp is the journal deadline in milliseconds, explicitly a logical correlation timestamp, not an observed completion time. No terminal timestamp or original actor exists in version 1. Public client attribution and runtime audit policy remain gated.

Before deletion the adapter appends and syncs that exact event to the ordinary append-only audit sink, then inserts or verifies its SQLite mirror and deletes only the matching projection in the same transaction. A file-only event is possible on rollback and remains evidence of reconciliation intent, not proof that SQL consumption committed. Normal audit startup replay can insert this event before reconciliation; therefore an existing matching event plus a matching pending row must still consume the row. Missing pending state succeeds only with the exact durable event already in SQLite. It never invents success for a missing projection without evidence. Other pending IDs fail closed even on replay.

A retry can append the identical same-ID file record again. Ordinary replay accepts identical duplicates. SQLite has exactly one event and no duplicate consumption. This avoids treating SQLite alone as proof of the independent file sink after rollback/reopen. An audit sink failure retains the pending projection and latches the existing unhealthy Log; reopen/replay is required before retry. Journal acknowledgement happens only after SQL COMMIT. Failed acknowledgement leaves replay safe; no new nonce is minted. A visible acknowledged record must sync the journal directory again before Reconcile reports success, because an earlier post-rename fsync can have failed.

A deferred foreign-key COMMIT failure must explicitly roll back the pinned SQL connection before returning it to the pool. Cleanup failure discards the connection. Store lifetime flock and tracked operation draining remain unchanged. Tests use owned scratch journals, SQLite, a real scratch audit file and injected sink/SQL failures only. There is no host restoration, systemd operation, CLI/RPC/startup wiring, new apply admission, terminal reuse, migration activation, or power-loss acceptance.
